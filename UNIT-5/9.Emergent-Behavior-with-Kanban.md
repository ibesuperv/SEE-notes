# Emergent Behavior with Kanban

## 1. Definition of Emergent Behavior

Emergent Behavior in Kanban is the natural improvement in the behavior of teams, managers, and stakeholders that occurs when the workflow is visualized and managed using Kanban practices.

Traditional organizations often follow a Command-and-Control approach where managers make detailed schedules, assign tasks, and closely monitor developers. This often leads to inaccurate estimates, unrealistic deadlines, stress, and burnout.

Kanban follows Systems Thinking, where the focus is on improving the overall workflow rather than controlling individual developers. It reduces:

- Muda (waste)
- Mura (unevenness)
- Muri (overburden)

This makes the entire development process more predictable and efficient.

Before Kanban, managers and developers often blame each other for project delays. Managers may think developers are working slowly, while developers believe delays are caused by approvals, testing, or changing requirements.

Kanban visualizes the complete workflow using a Kanban board. This allows everyone to see where work is actually delayed, creating a common understanding of the problem and reducing misunderstandings.

## 2. How Emergent Behavior Occurs (The Multi-Manager Case Study)

### The Problem (Before Kanban):

In many companies, multiple managers send competing feature requests to the dev team. Each manager claims their feature is the highest priority, putting developers under immense pressure, forcing multitasking, and causing late delivery.

### The Kanban Solution:

1. All feature requests are placed in an **Incoming Queue** column on the Kanban board. 2. The team sets a strict **WIP Limit** (e.g., maximum 5 items) on the Queue.

```text
       [ Manager A ]       [ Manager B ]       [ Manager C ]
             \                   |                   /
              v                  v                  v
          +-------------------------------------------+
          |           Incoming Queue (WIP: 5)         |
          |  [Feature A1] [Feature B1] [Feature C1]   |
          |  [Feature A2] [Feature B2]                |  <-- WIP Limit Full!
          +-------------------------------------------+
                                |
                                v
                    [ Dev Team Starts Work ]
```

### Emergent Behavioral Changes :

- **Eliminating Blame:** When the queue reaches 5 items, a manager cannot add a new request. Managers realize the limit is a system constraint, not developer refusal.
- **Manager Collaboration:** Managers must meet and negotiate among themselves to swap or remove features to free up a slot.
- **Eliminating Magical Thinking:** Shields developers from scope pressure, allowing them to focus on completing active work items ("stop starting, start finishing").
