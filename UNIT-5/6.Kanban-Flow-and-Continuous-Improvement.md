# Kanban, Flow, and Constantly Improving: The Principles of Kanban
*(Based on Andrew Stellman & Jennifer Greene, "Learning Agile" - Chapter 9)*

> "Kanban is not a software development lifecycle methodology or an approach to project management. It requires that some process is already in place so that Kanban can be applied to incrementally change the underlying process."
> — *David Anderson, Kanban*

---

## 1. What is Kanban?
Kanban is a method for process improvement used by agile software teams. Instead of replacing existing processes, teams start by understanding how they currently build software and make gradual, evolutionary improvements over time.

### 1.1 The Lean Connection
*   **Lean Mindset:** Kanban requires a lean thinking mindset. It applies Lean values and principles to a team's workflow.
*   **Eliminating Waste:** The primary focus is eliminating waste from the software development process. This includes the three types of waste defined in Lean:
    1.  **Muda:** Futility / non-value-added work (wastes of time, defects, overproduction).
    2.  **Mura:** Unevenness / inconsistency in workflow.
    3.  **Muri:** Overburdening of people or systems.
*   **David Anderson (2010):** Adapted Kanban from manufacturing to software development: *"The Kanban Method introduces a complex adaptive system that is intended to catalyze a Lean outcome within an organization."*

## 2. Comparing Focus: Kanban vs. Scrum vs. XP

| Framework / Method | Primary Focus | Key Areas |
| :--- | :--- | :--- |
| **Scrum** | **Project Management** | Scope of work, sprint planning, meeting delivery schedules, and ensuring the product meets stakeholder needs. |
| **Extreme Programming (XP)** | **Software Development** | Technical excellence, developer environment, coding habits, and producing code that is simple and easy to change. |
| **Kanban** | **Process Improvement** | Understanding the workflow, identifying waste/inefficiency, and incrementally improving the delivery process. |

## 3. Principles and Practices of Kanban
Kanban has a set of foundational principles and core practices (codified via the Kanban Yahoo! group):

### 3.1 Foundational Principles (The Starting Point)
1.  **Start with what you do now:** Do not disrupt the existing workflow. Treat the current process (even if chaotic or plan-driven) as the baseline.
2.  **Agree to pursue incremental, evolutionary change:** Agree as a team to make small, continuous improvements rather than massive, risky overhauls.
3.  **Initially, respect current roles, responsibilities, and job titles:** Avoid creating new roles (like ScrumMaster/Product Owner in Scrum) upfront. Respecting current roles prevents friction and recognizes their part in the existing system.

### 3.2 Core Practices
1.  **Visualize:** Draw out the workflow so everyone can see how work items progress.
2.  **Limit WIP (Work in Progress):** Restrict the number of active tasks at any one time to prevent bottlenecking and overburdening.
3.  **Manage Flow:** Monitor and optimize how work moves through the system.
4.  **Make Process Policies Explicit:** Write down the rules and steps the team follows so there is no ambiguity.
5.  **Implement Feedback Loops:** Set up mechanisms (like standups or reviews) to gather data and improve.
6.  **Improve Collaboratively, Evolve Experimentally:** Use models and the scientific method (taking measurements) to run experiments and improve.

> **Shallow vs. Deep Implementation:**
> Teams do not have to adopt all six practices initially. Adopting only a few practices is called a **"shallow"** implementation. Over time, as teams adopt more practices and improve their capabilities, they progress to a **"deep"** implementation.

## 4. Finding a Starting Point & Evolving Experimentally
*   **Habitual Problems:** Root-cause analysis after a project is helpful, but teams often fall back into habitual patterns (e.g., delivering software only to find out users didn't want those features).
*   **Explicit Policies:** To fix habitual problems, Kanban teams write down their unwritten rules as **policies**. Writing them down helps the team examine their habits objectively without judging individuals.
*   **Systems Thinking:** Lean urges us to "see the whole" (systems thinking). A team is not just making disconnected decisions; they are operating within a system. Even a chaotic team has a system of unwritten rules ("tribal knowledge").
*   **Scientific Method:** Kanban teams use metrics to measure their current system's performance. They then implement a policy change, measure the results, and verify whether the change actually reduced waste (Amplify Learning).
*   **No Silver Bullet:** Since there is no single "best" set of practices for every team, Kanban focuses on letting teams evolve their own customized systems.

## 5. Systems Thinking: Stories Go In, Code Comes Out
From a systems thinking perspective:
*   The software team is a system that takes inputs (requirements, user requests, MMFs) and turns them into outputs (working code).
*   **Minimal Marketable Features (MMFs) / User Stories:** Flow through the system.
*   **Value Stream Mapping:** A Lean tool used to map the path of an MMF from inception to production, helping identify wasteful delays.

## 6. Kanban Board vs. Scrum Task Board
A common mistake is treating Kanban as a task board. They have fundamentally different purposes:

```mermaid
graph TD
    subgraph Scrum Task Board
        A[Sprint Backlog Tasks] --> B[To Do]
        B --> C[In Progress]
        C --> D[Done]
    end

    subgraph Kanban Board
        E[Work Item Lifecycle] --> F[Upstream: Analysis / Prioritization]
        F --> G[Development / Testing]
        G --> H[Downstream: Deployment / Ops Tracking]
    end

    style Scrum Task Board fill:#fbe9e7,stroke:#ff5722
    style Kanban Board fill:#e1f5fe,stroke:#0288d1
```

*   **Work Items vs. Tasks:**
    *   *Scrum Task Board:* Tracks **tasks** (the specific developer actions needed to build a feature during a sprint).
    *   *Kanban Board:* Tracks **work items** (single, self-contained units of value like user stories or customer requests). Tasks are considered the "cogs" that push the work items through the columns.
*   **Scope of Visibility:**
    *   *Scrum Task Board:* Only active during a sprint. It only shows what is "To Do", "In Progress", or "Done" by the dev team.
    *   *Kanban Board:* Displays the **full lifecycle** of the work item. This includes upstream phases (e.g., how the Product Owner prioritizes ideas) and downstream phases (e.g., tracking deployment by operations).
*   **Exposing External Blockers:**
    *   Scrum teams are often blamed for late deliveries when the delay is actually due to long design review cycles beforehand or slow deployment pipelines afterward.
    *   A Kanban board visualizes these external steps, making bottlenecks outside the dev team's control explicit and visible to stakeholders.
*   **Flow Predictability:** By tracking work items across their whole lifecycle, Kanban improves the predictability of flow, which helps in long-term project planning and scheduling.
