# Agile Development Techniques
*(Based on Ian Sommerville, "Software Engineering", 9th Edition - Section 3.2)*

## 1. Introduction to Extreme Programming (XP)
*   **Origin:** Coined by Kent Beck (1998). The name comes from pushing recognized good practices (like iterative development, testing, and code reviews) to **"extreme" levels**. 
*   **Speed:** In XP, multiple new versions of a system may be developed by different programmers, integrated, and tested in a single day.
*   **Relationship to Agile Manifesto:** 
    1.  *Incremental Development:* Supported by small, frequent releases based on simple customer stories.
    2.  *Customer Involvement:* Supported by having a continuous customer representative on the team.
    3.  *People, Not Process:* Supported by pair programming, collective ownership, and a sustainable development pace (no extreme overtime).
    4.  *Change is Embraced:* Handled via frequent releases, test-first development, refactoring, and continuous integration.
    5.  *Maintaining Simplicity:* Supported by constant refactoring and simple designs that do not guess future changes.
*   **Practical Use:** Original XP has proved difficult to integrate with standard business culture/management. Hence, companies usually "pick and choose" XP practices or combine them with management-focused agile methods like **Scrum**.

## 2. Extreme Programming Practices (Summary)

| Practice | Description |
| :--- | :--- |
| **Incremental Planning** | Requirements are recorded on "story cards" (user stories). Stories are included in a release based on priority and available time. Developers break stories into "tasks". |
| **Small Releases** | Develop the minimal useful set of functionality first. Releases are frequent and incrementally build on the first release. |
| **Simple Design** | Design is carried out to meet current requirements only. No effort is spent anticipating future changes. |
| **Test-First Development** | An automated unit test framework is used to write tests for a new piece of functionality *before* it is implemented. |
| **Refactoring** | Continuous improvement of code structure and readability. Developers refactor code as soon as a potential improvement is spotted. |
| **Pair Programming** | Developers work in pairs, checking each other's work and providing support to always do a good job. |
| **Collective Ownership** | No individual "ownership" of modules. Pairs work on all areas; anyone can change any part of the code. |
| **Continuous Integration** | Tasks are integrated into the main system as soon as they are complete. All unit tests must pass after integration. |
| **Sustainable Pace** | Large amounts of overtime are unacceptable as they reduce code quality and medium-term productivity. |
| **On-Site Customer** | A full-time customer representative is part of the development team, bringing requirements and defining acceptance tests. |

## 3. Deep Dive into Key Agile Techniques

### 3.1 User Stories (Requirements)
Agile integrates requirements elicitation with development rather than having a separate upfront phase. Requirements are written as **User Stories** (scenarios of use described in the customer's own words).

#### Example: "Prescribing Medication" Story Card (Figure 3.5)
> **Prescribing Medication**
> Kate is a doctor who wishes to prescribe medication for a patient attending a clinic. The patient record is already displayed on her computer, so she clicks on the medication field and can select 'current medication', 'new medication' or 'formulary'.
> *   *If 'current medication':* System asks her to check the dose. If changing it, she enters the new dose and confirms.
> *   *If 'new medication':* She types the first few letters of the drug name. The system displays a list of possible drugs. She chooses the drug, checks the medication, enters the dose, and confirms.
> *   *If 'formulary':* System displays a search box for the approved formulary. She searches, selects the drug, checks it, enters the dose, and confirms.
> *   *Safety:* System always checks that the dose is within the approved range. If not, she is prompted to change it.
> *   *Confirmation:* Displays prescription for checking. She clicks 'OK' (records to audit database) or 'Change' (re-enters process).

#### From Stories to Tasks (Figure 3.6)
User stories are broken down into **Task Cards**. The developers estimate the effort needed for each task. The customer then prioritizes stories to identify what can be delivered in the next 2-week release.

```
+-------------------------------------------------------------+
| Task 3: Dose checking                                       |
|                                                             |
| Dose checking is a safety precaution to check that the      |
| doctor has not prescribed a dangerously small or large dose.|
|                                                             |
| 1. Using the formulary ID for the generic drug name, look   |
|    up the formulary and retrieve min/max dose.              |
| 2. Check prescribed dose against min/max.                   |
| 3. If outside range, issue error message.                   |
| 4. If within range, enable the 'Confirm' button.            |
+-------------------------------------------------------------+
```

#### Pros & Cons of User Stories
*   **Advantages:** Much easier for users to relate to compared to formal requirements documents or complex UML use cases. Helps get users involved early.
*   **Disadvantages (Completeness):** Hard to judge if enough stories cover all essential system requirements. Users are so familiar with their work that they often omit crucial details when telling stories.

### 3.2 Refactoring (Continuous Improvement)
*   **Traditional Philosophy:** "Design for change" (add generality early).
*   **XP Philosophy:** Discards this because changes anticipated often never happen, making it a wasted effort. Instead: **Design for today, refactor continuously.**
*   **Why Code Degrades:** In incremental development, local changes and quick workarounds degrade the software's structure. Code duplication and improper reuse make subsequent changes harder.
*   **Refactoring Actions:** Reorganizing class hierarchies, renaming variables/attributes, replacing duplicate code with library calls.
*   **Limits in Practice:** Development schedule pressure often causes teams to delay refactoring. Also, some major changes require architectural modification, which cannot be solved by simple code refactoring.

### 3.3 Test-First Development
Testing is central to the development process. Code cannot be written until a test for it exists and passes.

#### How it Works:
1.  **Understand Spec:** Developers must fully understand the specification of a task to write the test. This clarifies ambiguities early.
2.  **Write and Run Test:** Write the automated test. It fails initially (no code exists).
3.  **Implement Code:** Write the minimal code to pass the test.
4.  **Avoids "Test-Lag":** Prevents the development phase from getting far ahead of testing (which often leads to skipping tests under schedule pressure).

#### Example: Dose Checking Test Case Description (Figure 3.7)
*   **Input:**
    1.  A number in mg representing a single dose of the drug.
    2.  A number representing the number of single doses per day.
*   **Tests:**
    1.  Test for inputs where the single dose is correct but the daily frequency is too high.
    2.  Test for inputs where the single dose is too high or too low.
    3.  Test for inputs where `single dose * frequency` is too high or too low.
    4.  Test for inputs where `single dose * frequency` is in the permitted range.
*   **Output:** `OK` or an error message indicating the dose is outside the safe range.

#### Automated Testing & Frameworks
*   Tests are written as executable components before coding.
*   **Automated Test Frameworks** (like **JUnit** for Java) run all tests automatically when new code is integrated, immediately catching regression bugs.

#### Limits of Test-First Development:
1.  **Developer Shortcuts:** Programmers prefer writing functional code to testing. They may write incomplete tests or skip exception handling tests.
2.  **Difficult to Test UI:** Incremental unit tests for complex display logic, layout, and screen workflows are extremely hard to automate.
3.  **Illusion of Completeness:** Large test suites can give a false sense of security. Crucial, untested paths may still contain bugs if tests aren't regularly reviewed.

### 3.4 Pair Programming
In pair programming, two developers sit at the same computer. Pairs are created **dynamically** so everyone works with everyone else.

#### Advantages:
1.  **Collective Ownership:** Reflects Weinberg's concept of **egoless programming**—the team owns the software, not individuals. No single person is blamed for code errors; the team is collectively responsible for fixes.
2.  **Informal Code Review:** Actively reviews every line of code as it's written. It is cheaper and easier to organize than formal inspections.
3.  **Encourages Refactoring:** Since other team members benefit immediately from cleaner code, they actively support refactoring efforts.
4.  **Knowledge Sharing:** Reduces the risk to the project if key team members leave, as multiple people understand each part of the system.

#### Productivity and Studies:
*   *Williams et al. (2000) [Student Study]:* Found pair programming productivity is comparable to two people working independently. This is because pairs have fewer false starts, less rework, and spend less time debugging later.
*   *Arisholm et al. (2007) [Experienced Programmers Study]:* Found a significant loss of productivity compared to working alone. The quality benefits did not fully compensate for the overhead.
*   **Verdict:** While raw coding speed may drop for experienced developers, the benefits of shared knowledge, low project risk, and high code quality make it highly valuable.
